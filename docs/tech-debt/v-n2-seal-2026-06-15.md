### Fixes landed (2 LOW, proportionate hardening of the V-N2 diff; mechanical → reduced re-review)
- **F1 (spec §13.E-named; all 3 lenses) — overflow guard tightened to the int4 ceiling.**
  `settledBaseUnitsToCents` capped at `Number.MAX_SAFE_INTEGER` (9e15) but the credit columns
  (`amount_cents`/`balanceCents`/`totalRevenueCents`) are int4 (max 2,147,483,647). §13.E names "int4 max" as
  the bound. Changed the cap to `MAX_CREDIT_CENTS = 2_147_483_647n` (`settled-value.ts`). Now an out-of-band-corrupt
  value in (int4-max, MAX_SAFE] routes to the bounded frozen-amountCents fallback + `settled_value_unconvertible`
  alert instead of a DB `22003 integer out of range` rollback. Unreachable under exactAmount (tool prices are
  int4-bounded → never rejects a legitimate value). Non-vacuity: int4-max+1 cents (2147483648) now → null where
  the old guard returned 2147483648. Boundary test migrated to the int4 ceiling.
- **F5 (spec + core-invariant) — write/read key-sync guard added (test-only).** The reconciler READS the value
  via `SETTLED_VALUE_BASE_UNITS_KEY`; the ledger writers WRITE it as an inline SQL literal. A future rename of
  the constant that missed the two literals would write-under-A/read-under-B → the reconciler never finds the
  value → silent legacy-fallback → the over-credit vector returns unnoticed. Added a source-scan guard
  (`settled-value.test.ts`) asserting `ledger.ts` contains exactly 2 `jsonb_build_object('settledValueBaseUnits'`
  occurrences == the constant (mirrors credit-writer-census / verifier-exactamount-census). Non-vacuous (rename
  → 0 ≠ 2 → RED). No sealed-writer perturbation (test-only).
