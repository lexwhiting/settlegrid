## 1. Intent — why this chunk exists

**Goal (one sentence):** stop a client **retry of a timed-out metered proxy call** from being **charged twice** — add a MINIMAL idempotency gate so the second, logically-identical request does not run the money debit again.

**Why now / who consumes it.** This is **G3-3** — a launch-gate MONEY/BILLING blocker. `consumers.globalBalanceCents` (and `consumerToolBalances.balanceCents`) is real spendable balance the proxy **debits** to pay for tool invocations. Today the metered path has **NO idempotency**: a client whose call times out on their side (while SettleGrid's upstream still returns 2xx) and **retries** runs a fresh `handleProxy`, which **debits again** — the customer is billed twice for one logical call. The roadmap's escape hatch ("or document retry-billing") was **REMOVED** — documenting the behavior does not close the risk. **Brand-asymmetry is essential:** a double-charge is a trust/brand disaster; a missed charge is a minor revenue leak. When the dedup decision is ambiguous, **err toward NOT charging** (dedup), never toward charging.

**What the output enables.** A metered proxy that charges **at most once per logical request** within the client-retry window, with a **pinned regression test** so the guarantee stays closed under `web-ci`.

## 5. The load-bearing decisions most likely to be SILENTLY WRONG (audit concentrates here)

### LBD-1 (AUTHORITATIVE — the crux) — the gate must guard the DEBIT, not the `invocations` record
The roadmap literally says "dedup on the `invocations` insert." **That phrasing is a trap.** The `invocations` insert (F6) is a **fire-and-forget record**; the money moves at the **DEBIT** (F3, `:911`/`:673`/`:2679`). Adding a unique key to `invocations` + `onConflictDoNothing` would let the **debit fire again** on a retry and only dedup the *record* — the double-charge survives, and worse, you could end with a charge and no record. **RESOLUTION:** the idempotency gate is a **check-or-claim that PRECEDES the debit** and, on a duplicate, **skips the debit entirely, does NOT re-forward upstream, and returns a minimal "duplicate — not re-charged" response** (no stored-response replay — that is the "full framework" the queue forbids). Apply it at **all THREE debiting sites** (#1 cache-hit, #3 main, #6 failover) via **one shared helper** (a single implementation, not three copies). **Failure mode if mis-decided:** the double-charge stays open (dedup the record, not the debit), or two of three sites are missed.

### LBD-2 (FOUNDER-DECISION REQUIRED — key SOURCE + STORE; the "protects nobody" trap) — RECOMMENDED below
Two independent choices, each with a silent-wrong version:

**(2a) Key SOURCE.** A **client `Idempotency-Key` header** is semantically cleanest (the client declares "same logical request") — but **F9: no caller sends one and the SDKs have no retry loop, so a header-only gate protects ~zero live traffic** = exactly the paper-close the roadmap's removed-escape forbids. A **server-derived key** (reuse the already-computed request identity: `consumerId + toolId + method + hashBody` from F10, short TTL) protects **real live retries with no client change** — at the cost of **false-deduping two *intended* identical calls within the window** (a missed charge — the brand-safe direction per §1).
**(2b) STORE.** **Redis short-TTL** (atomic `SET NX EX <ttl>`, self-expiring, mirrors the x402 dedup F8, **no schema migration**) — but **fails OPEN on a Redis outage** (F13: dedup lapses during an outage → a double-charge is possible only then, only for a client that times-out-and-retries in that window). **DB-durable** (a `0018` dedup table/column + `ON CONFLICT` + a growth-sweep) — durable/fail-closed but heavier and needs unbounded-growth management; unnecessary given the retry window is **seconds**.

**RECOMMENDED (minimal + actually closes the LIVE risk; founder to confirm 2a/2b):**
- **Key** = an explicit client `Idempotency-Key` header **when present** (bounded/validated), **else** a **server-derived** key `sha256(consumerId : toolId : method : hashBody(...))` (reuse F10). This closes live retries today AND honors well-behaved clients.
- **Store** = **Redis**, atomic `SET dedupKey 1 NX EX <TTL≈60-120s>` (the client-retry window). No migration.
- **Documented residuals** (founder-accepted, brand-asymmetric): (i) Redis-outage fail-open (bounded, rare); (ii) false-dedup of two intended-identical calls within the TTL (missed charge — safe direction); (iii) a retry after the TTL re-charges (acceptable — the window is seconds).
- **Alternative if the founder wants durable/fail-closed:** the DB `0018` table + `ON CONFLICT DO NOTHING RETURNING` + a TTL sweep. Flag: heavier, and DC-14 migration care.

**Failure mode if mis-decided:** a header-only gate that protects no live traffic (G3-3 closed on paper, double-charge still live); or a fail-open store with an unstated residual; or false-dedup semantics the founder never signed off on.

### LBD-3 (DC-06 inverse trap) — claim/charge/release sequencing under concurrency
Mirror the `processedWebhookEvents` shape (F11): **(1)** atomically CLAIM the key (`SET NX` / `onConflictDoNothing RETURNING`); **(2)** if the claim LOST (key already held) ⇒ duplicate ⇒ skip debit + return the duplicate response; **(3)** if WON ⇒ run the debit; **(4)** if the debit COLLECTED $0 (insufficient funds / CAS-miss / upstream non-2xx ⇒ `actualCost 0`) ⇒ **RELEASE the key** (Redis `DEL` / delete the row) so a legitimate later retry (after top-up) can charge. Two concurrent retries must serialize on the atomic claim so **exactly one** debits. **Failure mode if mis-decided:** a claimed-but-uncharged key permanently deduping a legit retry (customer can never be charged / a stuck state); or a claim-after-debit ordering that races two retries into a double-charge; or releasing the key even on a *successful* charge (re-opening the double-charge).

## 5.5 — PLAN-AUDIT FOLDS (5-lens high-stakes fan-out + integrator live-verify, 2026-07-01 — AUTHORITATIVE; these AMEND §5/§6)

Folds are AUTHORITATIVE.

**CONFIRMED (no change):** LBD-1 (gate the debit not the fire-and-forget record) — the three `invocations` inserts (`:722/:1016/:2729`) are all `.then().catch()` AFTER their debit; F4's three money-debiting sites (`:676/693`, `:912/932`, `:2681/2697`) are the COMPLETE set; exactly one debit fires per request (cache-hit returns `:743`; failover returns before the main debit); the atomic `SET NX` serializes two concurrent byte-identical retries to exactly one `'OK'`; the Redis option needs NO `invocations` schema change; crypto-rail scope-out is correct.

**FOLD 1 [HIGH — convergent: SEAM+literal-exec+money+schema] — ONE claim BEFORE the upstream forward, NOT a per-debit-site gate.** LBD-1's "do NOT re-forward upstream" CANNOT hold at a debit-site gate: the `safeFetch` forward (`:780` main, `:2660` failover) PRECEDES its debit (`:911`/`:2679`), so a debit-site claim lets a duplicate RE-EXECUTE a possibly-non-idempotent upstream (double send-email/place-order) before being deduped. **RESOLUTION:** place a SINGLE claim after cost/fraud/balance-pre-check, **after body capture (`:661`) and before the cache check + forward (`~:662`)**, governing all three paths. On a duplicate the request returns EARLY — before any forward, debit, developer-credit, or `invocations` insert — which ALSO resolves the money lens's "skip must skip the whole billing block at #1/#6 or the developer is double-credited" (the duplicate never reaches any billing block). **Reuse the in-scope `requestBody` — do NOT re-read (`await request.text()` a second time throws; the body is consumed at `:657`).**

**FOLD 2 [HIGH — convergent: atomicity+money+schema; fact-verified] — TRI-STATE claim result (won / duplicate / Redis-down); do NOT let `tryRedis` collapse duplicate and outage.** `getRedis().set(k,'1',{nx:true,ex})` returns `'OK'` (won) or `null` (key exists = duplicate); `tryRedis` ALSO returns `null` on a Redis outage (`redis.ts:22-28`, verified). A 2-state helper that maps `null→duplicate` dedups EVERY request during an outage; mapping `null→charge` double-charges every retry during an outage. **RESOLUTION:** mirror the circle-nano tri-state EXACTLY (`settle.ts:326-332`): compute `res === 'OK'` INSIDE the `tryRedis` closure (→ `true` won), a strict `=== false` is duplicate, and a `null` is Redis-down. Map won→charge, duplicate→**skip**, down→FOLD 3.

**FOLD 3 [FOUNDER DECISION — atomicity+schema recommend fail-OPEN; money lens flags it] — Redis-down (`null`) fail direction.** RECOMMENDED: **fail-OPEN (proceed + charge) + emit a `money_loss` alert** (mirroring the academic auto-confirm tripwire + `proxy.balance_race_unpaid_invocation`). Rationale: fail-CLOSED (skip/don't-charge on outage) = a TOTAL money-rail revenue outage for the outage window (every call free); fail-OPEN preserves availability, and the rare double-charge (outage ∩ timing-out-retrying client) is detectable via the alert + refundable. **FOLD 4 [FOUNDER DECISION — money+schema; the key-source tradeoff, sharpened] — key source + the poll-collapse residual.** Honor an explicit client **`Idempotency-Key` header when present** (primary, semantically correct — a poller varies it, a retrier reuses it); ELSE a server-derived key `idem:charge:sha256(consumerId:toolId:method:hashBody(method+requestBody))` (best-effort). **FOLD 6 [MED — convergent: atomicity+SEAM+literal-exec+money] — release only at KNOWN no-charge exits, and AWAIT it.** Release (`await tryRedis(() => getRedis().del(key))`) on the paths where no money moved AND no charge is intended: the upstream-error catch (`:781`), SSRF block, non-2xx-without-failover, and pre-debit early returns.
