## What + why
On-chain settlement is broadcast-then-confirmed. The live settle path (circle-nano A2 + x402 B1.2) writes a `pending` ledger row with the broadcast txHash in `external_ref` and flips it to terminal ONLY on a confirmed receipt. A settle that times out, crashes mid-wait, or is broadcast during a gas outage leaves the row stuck `pending` with nothing to flip it afterward. B1.4 re-checks those rows on-chain and flips them.

### Funds-safety design (mirrors settle.ts `applyOutcome`)
- `settled` receipt → `markSettlementSettled`. `reverted`+nonce-FREE → `markSettlementFailed`. **`reverted`+nonce-CONSUMED (a concurrent tx settled it) → leave `pending` (NOT failed)**. `unconfirmed`/`unsupported` → leave `pending`/skip. A reverted/unconfirmed tx is NEVER recorded `settled`.
- Every flip is guarded `WHERE settlement_status='pending'` → terminal-safe; a race with the live settle path or another run resolves to one winner.
- Covers circle-nano + x402 (the only on-chain `pending` rails — ap2 settles synchronously as `settled`).

3. **`flipped:false` counts as `settled`/`failed` in the summary** (a row already terminal via a concurrent winner). On-chain outcome is correct; the run-summary slightly over-reports transitions (logged with `flipped:false`). Optional: a `*-noop` tally.

For circle-nano this is covered upstream (the verifier enforces the payee before submit). For x402 facilitator-mode the txHash is trusted from the facilitator — a pre-existing B1.2 boundary; the reconciler re-confirms on-chain success, which is strictly MORE checking than B1.2 did.
