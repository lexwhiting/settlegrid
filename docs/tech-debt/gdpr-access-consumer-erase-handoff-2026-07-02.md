## 1. Intent — why this chunk exists

**Goal (one sentence):** make SettleGrid's GDPR data-subject rights REAL and free for the two subject classes that today can't exercise them — (G5-2) un-paywall the developer's Art.15/20 data **access/portability** export (today gated to Scale+), and (G5-3) give a **consumer** (a non-developer-twin end-user) a working Art.17 **erasure** path (self-delete OR an honest "email us" that is actually honored) — while (G5-1) the MFA step-up on the developer-deletion control is already shipped and live, needing only its operator live-smoke.

This chunk makes the published promise true for code-closeable paths.

**What the output enables.** Any developer (any tier) can export their own personal/business data for free (Art.15/20); any consumer can have their identifying data erased (Art.17) through a path the product actually honors — closing the gap between the published privacy promise and the shipped behavior.

## 5. The load-bearing decisions most likely to be SILENTLY WRONG (audit concentrates here)

### LBD-1 (G5-3 — the consumer-erase DESIGN: the "passes every test yet wrong" hazard)
A consumer self-delete must get THREE things right simultaneously, each a silent-failure trap:
- **(a) ANONYMIZE-IN-PLACE, never DELETE (F6/F7).** The naive `DELETE FROM consumers WHERE id=…` cascade-destroys `consumerToolBalances/apiKeys/invocations/purchases` (all `NOT NULL ON DELETE CASCADE`) — **including foreign developers' invocation + financial history**, silently corrupting other parties' records and the platform's billing ledger. The erase MUST mirror `compliance.ts:783-839`: per-row `email → deleted-<id>@…`, null the identifying columns, **REVOKE** (not delete) the consumer's apiKeys, null `ipAllowlist`, delete the Supabase auth user. **Failure mode:** destroyed foreign financial data + a broken ledger.
- **(b) DEVELOPER-TWIN handling (F6).** If the consumer shares an email with a developer account, a consumer-only erase that anonymizes the consumer row but LEAVES a live developer row with the real email creates a split identity (dev row real email; consumer row `deleted-<id>`) — and the developer-delete cascade keys on `lower(trim(email))` (`:657-664`), so after the consumer email is anonymized a later dev-delete no longer matches the (now-deleted) twin. **RESOLUTION (name one):** either (i) detect a developer twin (same `supabaseUserId` OR normalized email) and REFUSE with a redirect ("you have a developer account — deleting it erases both; use the developer account-deletion"), OR (ii) erase only the consumer identity and document the residual. **Failure mode:** an inconsistent half-erased identity that neither path later completes.
- **(c) ACADEMIC-RECYCLE $500 interaction (F8).** Erasing/freeing the consumer email with `academicGrantedAt` on the freed row lets the same mailbox re-mint $500 — a NEW lower-friction path than the already-accepted dev-delete loop. **RESOLUTION (name one):** either (i) record the academic grant on an erasure-SURVIVING key (a salted hash of the verified email/domain) that the grant check reads and the erase MUST NOT reset — the queue's recommended fix (`:160` #2) — OR (ii) explicitly inherit the founder-accepted-residual framing AND ensure the consumer erase is **no lower-friction** than the existing dev-delete loop (e.g. require `{ requireEmailVerified: true }` + the same detectability/alerting), documenting it. **The plan audit decides which; do NOT silently ship a lower-friction $500 recycle.** **Failure mode:** an un-budgeted credit-farming loop.

**ALTERNATIVE to a self-delete endpoint (the roadmap's second option):** an honest **"email us to delete" fallback that is actually honored** — the `/privacy` promise already exists (F9); "actually honored" = confirm `privacy@` is a monitored inbox + write a documented manual-erasure runbook (an operator/§P deliverable, not code). Lower ENG effort, but shifts the compliance burden to a human process whose reliability can't be unit-tested. **RECOMMENDED (plan proposes):** build the self-delete endpoint — the codebase already has every primitive (F5/F6), so it is only modestly more work than a manual process and avoids the unmonitored-inbox risk; the honest-email path stays as the documented BACKSTOP for consumers who can't sign in. The audit rules if this is right-sized for pre-PMF.

### LBD-2 (G5-2 — the un-gate SCOPE PRECISION)
Removing the `data_export` tier gate must un-gate EXACTLY the Art.15/20 personal-data export and nothing else. The dangerous errors: (a) un-gating the export but LEAVING `/pricing` selling "Data export (GDPR)" as Scale-only (F3) → a false published pricing claim (honest-claims regression); (b) accidentally un-gating the SEPARATE paid `advanced_analytics`/`consumer_insights`/`audit_logs`-dashboard features that share tier plumbing (the export's `audit_logs` CATEGORY is the subject's own access log — distinct from the `audit_logs` dashboard FEATURE flag; do not conflate); (c) un-gating in a way that lets a free-tier dev pull an EXPENSIVE/unbounded export as an abuse vector (the export is already rate-limited `data-export:uid` — confirm that's sufficient, don't add a new gate that re-paywalls). **RESOLUTION (RECOMMENDED):** delete the `hasFeature(… 'data_export' …)` gate in `data-export/route.ts` so the GDPR export is free for all tiers, KEEP the existing rate-limit, and reconcile the `/pricing` + `pricing-section` copy so "Data export (GDPR)" is no longer sold as a Scale-exclusive (reframe to e.g. scheduled/bulk analytics export if a paid tier remains, or drop the line). The counsel DSAR-formality question (§C) does not block this. **Failure mode if mis-decided:** a still-paywalled right, a newly-false pricing claim, or an accidentally-free paid analytics feature.

### LBD-3 (Art.15 CONSUMER access symmetry — scope boundary, likely OUT)
G5-2 names the DEVELOPER export; G5-3 names CONSUMER erasure. Note the asymmetry: a consumer gets erasure (G5-3) but the blockers list NO consumer data-ACCESS/export path. Is that a gap this chunk must close, or a separate future blocker? **RESOLUTION:** the roadmap enumerates exactly {G5-1, G5-2, G5-3}; a consumer access/export endpoint is NOT a listed blocker → **OUT of scope** (record as a noted residual for the roadmap, do NOT build it — scope creep). The audit confirms this boundary rather than expanding it.
