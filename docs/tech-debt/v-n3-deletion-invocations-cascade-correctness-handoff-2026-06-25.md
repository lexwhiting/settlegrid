## 0. The defect (what the investigation proved — read first)
`processDataDeletion` (`apps/web/src/lib/settlement/compliance.ts:457`, **DORMANT — zero production callers**, the only wired compliance route is developer data-EXPORT) intends, at **step 4** (`:716-722`, comment: *"Null out PII metadata on invocations (**keep financial data**)"*), to KEEP the invocation rows and only null their `metadata`. But:

- `invocations.api_key_id` is **`NOT NULL` … `ON DELETE cascade`** → `api_keys.id` — confirmed in BOTH `schema.ts:325-327` AND the migration `apps/web/drizzle/0000_polite_moonstone.sql:260` (`ON DELETE cascade`). It is the **sole active cascade vector** into `invocations` (`toolId`→tools and `consumerId`→consumers are also CASCADE, but tools/consumers are *anonymized, not deleted*, so those cascades are inert).
- **Step 2** (`:668`) `tx.delete(apiKeys).where(inArray(apiKeys.consumerId, ids))` deletes the consumer-twin's keys (all tools, incl. foreign).
- **Step 3** (`:711-713`) `tx.delete(apiKeys).where(inArray(apiKeys.toolId, toolIds))` deletes the subject's tools' keys.

In real Postgres, deleting those keys **cascade-deletes every `invocations` row that references them** — i.e. the twin-as-consumer's invocations on ALL developers' tools (step 2) and all invocations on the subject's tools (step 3) — **before step 4 runs**. So:
1. **Step 4 is a no-op in prod** (its target rows were just cascade-deleted). The just-shipped `anonymized:['invocations.metadata']` claim is "true" only by accident (rows deleted, not metadata-nulled) via an undocumented mechanism.
2. **Cross-principal over-deletion:** a consumer's deletion destroys FOREIGN developers' invocation/usage/revenue-analytics rows — contradicting step 4's own "keep financial data" intent.
3. **Invisible to the suite:** the drizzle test-mock does NOT enforce FK cascade, and there is no real-Postgres integration test (the SLICE-5 ③ flagged exactly this missing test). DC-05 / DC-14 blind spot; the prior mock-based reviews (incl. the enable-disclosure ③) structurally could not see it.

All DORMANT today (no caller, prod empty) → no live data lost; the fix is correctness + honesty hardening of code that must be right *before* a deletion route is ever wired.

## 1. Intent — why, who consumes, what it enables
A deletion subject's GDPR erasure must (a) remove their PII and (b) NOT destroy other parties' retained financial/usage records. Today the apiKey cascade does the opposite of step 4's stated intent. **This chunk makes the deletion KEEP invocation rows (financial/usage records) while erasing the subject's PII**, proves the real row-level behavior with a Postgres-faithful integration test (the missing test the cascade hid behind), and makes the deletion-export disclosure honest about what truly survives. **Consumers:** the DC-16 honesty posture + the (future) deletion-route wiring cluster, which can then be built on a deletion that is actually correct. **Enables:** a trustworthy erasure-proof artifact and removal of a latent cross-principal data-loss bug.

## 2. The fix — REVOKE-and-anonymize the apiKeys instead of DELETE (LB1)
Change `processDataDeletion` **steps 2 and 3** from `tx.delete(apiKeys)` to an **UPDATE that revokes + anonymizes** the same rows (same predicates: step 2 `inArray(apiKeys.consumerId, ids)`, step 3 `inArray(apiKeys.toolId, toolIds)`):
- `status: 'revoked'`, null `keyHash`, null `keyPrefix`, null `ipAllowlist` (the credential + the IP-allowlist PII jsonb). Optionally set `revokedAt` if the column exists on `api_keys` (verify — the developer-keys table has it; confirm `apiKeys` has it before using).
- Keeping the row (not deleting it) means the `invocations.api_key_id` FK target SURVIVES → **no cascade** → invocations persist → step 4 nulls their metadata as intended.
- **Safety (de-authentication):** a `status:'revoked'` key with a nulled `keyHash` cannot authenticate — the proxy/SDK auth path looks up by `keyHash` (`proxy/[slug]/route.ts:162`), reads `apiKeys.status` (`:146`), and returns `API_KEY_REVOKED` 401 (`:177`); nulling `keyHash` also makes the `inArray(apiKeys.keyHash, …)` lookup miss. This is exactly how the product already revokes keys (`consumer/keys/[id]/route.ts:63`, `dashboard/developer/api-keys/[id]/route.ts:72` — `status:'revoked'`), so revoke-not-delete is pattern-consistent and inherits the existing, tested revocation guarantee. **The build MUST confirm EVERY apiKey auth/lookup path rejects a revoked / null-keyHash key** (proxy + every `sdk/*` route that does `inArray(apiKeys.keyHash, …)` — `meter`, `meter-with-metadata`, `validate-key`, `test-validate`).
- **Postgres note:** the `api_keys_key_hash_idx` UNIQUE index tolerates multiple NULL `keyHash` values (Postgres treats NULLs as distinct), so nulling `keyHash` across many revoked rows is safe.
- **Idempotent** on retry (UPDATE, like the consumers/developers/tools anonymize steps). Step 1b (`developerApiKeys` DELETE, `:621`) is a DIFFERENT table that `invocations` does NOT reference — verify it has no harmful inbound cascade; if clean, leave it (out of scope).

This also fixes the cross-principal over-deletion as a byproduct (foreign developers' invocations now survive) and makes the EXISTING `anonymized:['api_keys','invocations.metadata']` disclosure claims genuinely accurate (the code now anonymizes rather than deletes).

## 11. PLAN-AUDIT FOLDS — BINDING CORRECTIONS (2026-06-25; supersede any conflicting text above)
The pre-build plan audit (5 lens-distinct Opus-4.8 reviewers: fix-correctness / SEAM / literal-execution / DC-16 / scope+recurrence) CONFIRMED the core revoke-not-delete design and the cascade thesis, and verified de-authentication across all 5 apiKey auth paths (proxy + `sdk/{meter,meter-with-metadata,validate-key,test-validate}` — each matches `inArray(apiKeys.keyHash,…)` AND rejects `status!=='active'`). It surfaced the following sustained findings; ALL are folded here and are BINDING:

**F1 [HIGH — corrects §2] — REVOKE must be `status`-only + null `ipAllowlist`; do NOT null `keyHash`/`keyPrefix`.** `api_keys.key_hash` and `api_keys.key_prefix` are **`NOT NULL`** (`schema.ts:250-251` + migration `0000`), and `key_hash` carries a **UNIQUE** index (`api_keys_key_hash_idx`, `:263`). Nulling them throws a NOT-NULL violation → the whole deletion txn rolls back → the disclosure is never persisted (recorded-but-never-reached); a constant sentinel would violate the UNIQUE index. **The fix:** steps 2 & 3 become `tx.update(apiKeys).set({ status: 'revoked', ipAllowlist: null }).where(<same predicate>)` — `status:'revoked'` is the de-auth mechanism (this is EXACTLY how live revocation works — `consumer/keys/[id]/route.ts:63` sets status only), and `ipAllowlist` (nullable jsonb that can hold IPs = PII) is nulled. Do NOT touch `keyHash` (a one-way credential hash, not personal data; rendered useless by the status gate) or `keyPrefix`. **De-auth now rests solely on the status gate — verified airtight on all 5 paths.** `revokedAt` does NOT exist on `api_keys` (only `developerApiKeys`) → do NOT set it. (This supersedes the §2 "null keyHash/keyPrefix" bullet and its "Postgres NULL" note.)

**F2 [HIGH — corrects §3, §5 LB1] — the silently-wrong risk for LB1 is the NOT-NULL/de-auth-completeness, not key nulling.** Restate LB1: revoke must FULLY de-authenticate via `status='revoked'` alone (keyHash retained). The integration test MUST assert a revoked key cannot authenticate — take the "**assert the gate**" branch (assert the row is `status='revoked'` in the DB, which the verified status-gate turns into rejection) rather than importing the full Next.js route handlers into the node test.
