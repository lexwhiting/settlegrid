## 1. Intent — why this chunk exists

**Goal (one sentence):** two independent containment hardenings — (G4-3) flip the *credential-brute-force* rate limiters (`mfa-verify` + `claim-token`) from fail-**open** to fail-**closed** so a rate-limit-store outage can't evaporate brute-force protection, while KEEPING the erasure + LLM-cost limiters fail-open; and (G4-4) add an automated assertion that the load-bearing **money columns** in the live DB still match `schema.ts` (the prod schema is managed by `drizzle-kit push` with no down-migrations, and DC-14 already shipped a silent money-default once).

**Why now / who consumes it.** These are the last two **G4 (containment)** launch-gate blockers before the legal/email chunks. Both are pre-PMF safety nets: G4-3 protects the auth surface at launch (adversaries arrive); G4-4 is the tripwire for silent money-schema drift on a substrate that has no migration history and no rollback.

**What the output enables.** A brute-force limiter that stays closed on the credential surfaces when the store rejects, and a standing alarm that pages if a money column silently drifts from `schema.ts` in prod.

## 5. The load-bearing decisions most likely to be SILENTLY WRONG (audit concentrates here)

### LBD-1 (SCOPE PRECISION — the G4-3 crux) — flip EXACTLY {mfa-verify, claim-token}; keep {account-delete, LLM} open
The dangerous errors: (a) flipping `account-delete` (both buckets) → a rejecting Redis blocks a GDPR erasure request → **Art.17 violation** (F5); (b) flipping an LLM/cost path (`/api/ask`) → a rejecting Redis 503s a cost-bounded endpoint for no security gain (F6); (c) flipping the WRONG mfa bucket (status/enroll/unenroll instead of verify) → no brute-force benefit + a needless availability hit (F3); (d) MISSING a real credential-brute-force limiter the roadmap's "+ any real app-side credential limiter" clause anticipates. **RESOLUTION:** flip `{ failMode: 'closed' }` on exactly the FOUR call-sites: `mfa-verify:${ip}` (`auth/mfa/route.ts:113`), `mfa-verify:uid` (`:125`), `tools-claim:${ip}` (`tools/claim/route.ts:60`), `tools-claim:uid` (`:94`). The **scope/completeness lens MUST independently sweep every route that verifies a user-supplied secret/short-code against a stored value** (mfa TOTP, claim token, and confirm there is NO other: password/reset [F7 none], API-key validate [`sdk/validate-key`, `sdk/test-validate` — a 256-bit key, cost-bounded SDK path, NOT a short-code guess → OUT], recovery codes, unsubscribe tokens, webhook secrets) and confirm {mfa-verify, claim-token} is the COMPLETE executable set. **Failure mode if mis-decided:** an Art.17 regression, or a still-open brute-force surface shipped as "contained."

### LBD-2 (AUTHORITATIVE — the partial-coverage truth) — "fail-closed" closes only the REJECTION path, NOT the 5s hang
Per F8/F9: `failMode:'closed'` blocks when the store op **rejects**, but a **hanging** Upstash Redis still fails OPEN via the library's built-in 5s `timeout` race (returns `success:true` inside `limiter.limit()` before `checkRateLimit`'s catch runs). And the credential limiters share `apiLimiter`/`authLimiter` with fail-open routes (account-delete on `authLimiter`!), so you **cannot** set `timeout:false` on the shared limiter to close the hang path without breaking Art.17. **RESOLUTION (RECOMMENDED — minimal, scope-disciplined):** ship the `failMode:'closed'` flip (closes the rejection path — the named G4-3 deliverable) AND **document the hang-path residual explicitly** — a code comment at the flipped call-sites ("failMode:'closed' covers store REJECTION; a hanging store still fails-open via the Upstash 5s timeout race — see LBD-2") + a **§P note** ("brute-force fully closed only on store rejection; the hang path is backstopped by Supabase's own MFA/verify throttling"). Do NOT silently ship a half-fix as "fully contained." **Alternative (heavier, only if the audit deems the hang path unacceptable):** introduce DEDICATED limiters `mfaVerifyLimiter` / `claimTokenLimiter` (own `lazyLimiter`, `timeout:false` via a new `createRateLimiter` param) so the hang path also closes WITHOUT touching the shared limiters — more code, must not regress the shared fail-open routes. **The plan audit decides which; the RECOMMENDED path is document-the-residual (the roadmap scope is literally "flip to failMode:'closed'"; dedicated limiters are gold-plating beyond the named deliverable unless the audit finds the hang path is the dominant outage mode).** **Failure mode if mis-decided:** a false belief that brute-force is fully contained on any store outage (it isn't on a hang), or an Art.17 regression from reconfiguring a shared limiter's timeout.

### LBD-3 (G4-4 DESIGN — where the assertion lives + how it gets TEETH)
The naive designs fail: a **CI check** can't reach prod (F10, web-ci is secret-free) so it either can't run or checks a schema.ts-built DB **tautologically**; a **blocking startup throw** would self-DoS the app on a transient DB blip. **RESOLUTION (RECOMMENDED design):**
1. A pure manifest `src/lib/db/money-schema-manifest.ts` — explicit expected shape of the ~9 load-bearing money columns (F11): `{ table, column, dataType:'integer', notNull:true, default:'0'|null }`, plus the `ledger_entries_amount_positive` CHECK and the `payouts_one_processing_per_dev` partial-unique index.
2. A checker `verifyMoneySchema(db): Promise<Drift[]>` that introspects `information_schema.columns` (+ `pg_constraint`/`pg_indexes` for the check/index) and returns any mismatch (missing / wrong type / wrong nullability / wrong-or-absent default / missing constraint / missing index).
3. Wire into `instrumentation.ts` `register()` — **`nodejs` runtime + production only, FIRE-AND-FORGET, NON-BLOCKING, run-once (module guard)**: on drift → `logger.error('schema.money_column_drift', { drifts }, )` and add `'schema.money_column_drift'` to `MONEY_LOSS_KEYS` (`logger.ts`) so it PAGES; **never throw** (a schema-check failure must not take the app down — that would invert the containment goal).
4. **TEETH (DC-24):** a unit test that imports the drizzle table objects from `schema.ts` and asserts the **manifest matches schema.ts's actual column metadata** (drizzle exposes `.notNull`, column type, `.default` at runtime) — so the manifest can't silently diverge from schema.ts (fails RED if either side changes without the other); PLUS a `verifyMoneySchema` unit test with a MOCKED introspection result proving drift→returned and match→empty. **Do NOT** claim the unit test proves the LIVE prod schema matches (that's the startup check's job at runtime, against prod — a §S/§P note). **Failure mode if mis-decided:** a tautological check (manifest built FROM the same introspection it validates), a blocking startup throw that self-DoSes, or a toothless test that stays green when a money column's default drifts.
