### 1b. The reconciler's EXACT select + the trap + the guard-by-construction proof.

**The reconciler's exact SELECT** (`reconcile.ts:290-316`, verbatim WHERE):
```ts
db.select({ operationId, rail, externalRef, amountCents, accountId, metadata })
  .from(ledgerEntries)
  .where(and(
    eq(ledgerEntries.settlementStatus, 'pending'),
    inArray(ledgerEntries.rail, [...RECONCILABLE_RAILS]),   // RECONCILABLE_RAILS = ['circle-nano','x402']  (reconcile.ts:29)
    isNotNull(ledgerEntries.externalRef),
    lt(ledgerEntries.createdAt, cutoff),                     // cutoff = now − 5min (default)
  ))
  .orderBy(asc(ledgerEntries.createdAt))
  .limit(limit)                                              // default 25
```
Run in prod by the cron `GET /api/cron/settlement-reconcile` (`route.ts:35`), every 15 min (vercel.json),
auth'd by `CRON_SECRET`, IP-limited via `apiLimiter` (NOT `sdkLimiter` — disjoint from F1).

**The trap (re-derived live, matches post-B4:120-125).** A hop row written for `rail ∈ {x402,circle-nano}`
with a non-null `externalRef` satisfies **all four** WHERE conjuncts (`pending` ✓ `rail∈set` ✓
`external_ref NOT NULL` ✓ `created_at<cutoff` ✓ once 5 min old) → selected. In `reconcileOneRow`
(`reconcile.ts:96`), `parseSettlementOperationId(hopId, rail)` runs the **bare UUID** `operationId`
against `/^x402:(eip155:\d+):(0x…40):(0x…64)$/` (`reconcile.ts:69`) → **no match → `skipped-unparseable`**
(`reconcile.ts:104-107`). The row is never flipped, stays `pending`, and is **re-SELECTed every run
forever**, oldest-first, occupying one of the bounded **25** slots → starves legitimate pending
settlements at volume (+ log-noise).

**Crucial framing for the funds-SEAL:** mis-credit is **impossible** — the `skipped-unparseable` return
happens *before* any credit path (`reconcile.ts:104` precedes the `creditSettlement` at `:128`). **(H)
fixes a reconciler liveness / starvation hazard, NOT a money mis-credit hole.** (post-B4:121-122 confirms.)

**The guard MUST be hop-specific — proven.** The trap's fix cannot live in the shared writer
`recordSettlementEntry`, because that writer is the **legit on-chain settle path**:
`recordSettlementEntry` callers = `ap2/settle/route.ts:176`, `circle-nano/settle.ts:85`,
`x402/orchestrate.ts:136` — these legitimately write `pending` + `externalRef` rows for `x402`/`circle-nano`
with **parseable** `operationId`s (`network:from:nonce`) that the reconciler **must** select and flip. A
rail-enum guard in the shared writer would break real settlement. The **only** caller of the async hop
variant `recordSettlementEntryAsync` is `recordHop` (`sessions.ts:469`) — verified by grep (the ap2 hit is
a comment). **So the guard is one surgical condition at `sessions.ts:461-468`.**

**Guard-by-construction proof (mechanically testable without a real DB):**
  - The reconciler selects a row **only if** `rail ∈ RECONCILABLE_RAILS` (the `inArray`).
  - The guard ensures `recordHop` writes a settlement row **only if** `rail ∉ RECONCILABLE_RAILS`.
  - Both reference the **same constant** ⟹ a hop-written row's `rail` is never in the reconciler's
    selection set ⟹ **never selected.** ∎
  - The two sets cannot drift only if they are literally the same symbol. → **Single source of truth.**

**Guard form + placement (DECISION).** App-layer, at the single hop call site. `ledger_entries.rail` is
free **`text('rail')`** (`schema.ts:886`) — no pg enum, no existing CHECK on rail. Options weighed:
  - **DB CHECK constraint (migration).** Rejected as over-engineering: a CHECK that excludes
    `{x402,circle-nano}` *only for hop-shaped rows* is hard to express (can't cheaply distinguish a hop's
    bare-UUID opId from a legit `network:from:nonce` opId in SQL) and risks rejecting the legit settle
    path's rows. The single application writer already gives a by-construction guarantee. No migration.
  - **Shared constant location.** `RECONCILABLE_RAILS` is currently `const` (not exported) at
    `reconcile.ts:29`. **DECISION: extract to a dependency-light leaf module
    `apps/web/src/lib/settlement/rails.ts`** exporting `RECONCILABLE_RAILS` (+ `isReconcilableRail`),
    imported by **both** `reconcile.ts` and `sessions.ts`. Rationale: avoids coupling the session hot
    path to `reconcile.ts`'s import graph (viem / settle-engine), and makes the single-source-of-truth
    explicit. (Fallback if the audit prefers minimal diff: `export const` from `reconcile.ts` — one
    token. Recommended: the leaf module.)
  - **Behavior on an on-chain rail:** record the hop in `workflowSessions.hops` + `spentCents` as normal
    (budget accounting is authoritative and must not be blocked), **skip** the settlement-row write, and
    `logger.warn` a structured skip event so a future misuse is observable, not silent. Do **not** throw
    (budget is already incremented at `sessions.ts:446-453`; throwing would corrupt the hop).

### 1c. Durability — **keep lib-layer fire-and-forget.** DECISION.

Current: `recordSettlementEntryAsync` (`ledger.ts:476`, fire-and-forget, logs `settlement.ledger_write_failed`
without bubbling). Keep it. Rationale:
  - The hop ledger row is a **non-authoritative attribution/audit** record. Budget accounting — the only
    thing `finalizeSession` reads — is the **synchronous** JSONB-append + `spentCents` update
    (`sessions.ts:446-453`), which is NOT fire-and-forget. (post-B4:117-118: "the `hops` JSONB … is the
    authoritative per-hop record"; "zero code reads settlement rows by `session_id`.")
  - After the guard, hop settlement rows exist only for **off-chain** rails (the documented intent:
    `RecordHopInput.rail` examples are `stripe-connect`, `internal` — `session-types.ts:58`; `l402` is a
    *protocol* (`:61`) and `L402 hash` an *externalRef* format (`:69`), both off-chain w.r.t. the reconciler
    set). No on-chain money movement depends on them; a dropped row loses an audit entry, not money.
  - **Route-durable (`after()`) is rejected:** it would (i) break `recordHop`'s request-scope-free unit
    tests — the **B2-moot finding** (post-B4:126-127) — and (ii) require expanding the route's auth +
    zod surface (the activation we ruled OUT in §1a). ap2's durable `after()`
    (`ap2/settle/route.ts:171-176`) is the exemplar we are deliberately *not* copying here. Smaller change
    wins; the choice is documented honestly (audit-only, best-effort) rather than claiming false durability.

### 2c. Abuse-cost analysis for the loosening. **N = 5000/min/IP proposed.**

The session routes are **budget-capped and non-financial w.r.t. rate**:
  - `recordHop` cannot overspend — it rolls back on `available < 0` (`sessions.ts:423-429`); the session
    **budget** is the spend ceiling, independent of request rate.
  - `createSession` requires a positive budget and passes org/parent budget checks (`sessions.ts:56-110`);
    it **moves no money** — it inserts a `workflow_sessions` row + 3 Redis keys.
  - get/delegate/finalize/complete are budget-bounded state transitions.

So a higher per-IP session limit raises **infra load** (DB/Redis ops; createSession row-spam) but **not**
financial abuse. The bound to compare against: `proxy/[slug]` already permits **1000/min/IP** of actual
on-chain settlement attempts; 5000/min of budget-capped session ops is a **lower** financial-risk posture
than what the platform already accepts on the money proxy. The other ~20 `sdkLimiter` routes (incl. all
money paths) **stay at 1000/min** — unchanged. 5000/min (5×) gives a NAT egress fronting many agents
real headroom (e.g. 100 agents → 50/min/agent) while remaining bounded; it sits between the builder
(4000) and scale (16000) tiered sdk values (`rate-limit.ts:112-115`) as a sanity anchor.

> **N is the key F1 judgment call** — proposed **5000**, flagged for the audit (and founder if they want a
> specific posture). Applied **uniformly** to all 6 session routes (smaller change than splitting
> createSession onto a tighter limiter; createSession spam is bounded + non-financial). The audit may
> argue a tighter createSession limit; default is uniform. **[Phase-3 update: the audit DID flag the
> row-insert amplification; the split was adopted — create/delegate stay at 1000. See §6.4 + build plan.]**
