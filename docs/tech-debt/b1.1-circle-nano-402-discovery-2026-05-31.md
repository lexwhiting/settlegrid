## The gap B1.1 closes

The live circle-nano verifier requires `authorization.to === SETTLEGRID_USDC_RECIPIENT`, but the 402 "Payment Required" challenge never surfaced that recipient (nor the USDC contract / EIP-712 domain). So an external payer had no way to construct a valid authorization — the rail was LIVE but **not externally usable**. B1.1 makes the 402 self-describing.

## What shipped

The circle-nano 402 body now carries (all NEW, conditionally emitted):

| Field | Source | Purpose |
|---|---|---|
| `pay_to` (top-level) | `getCircleNanoRecipient()` | the `authorization.to` the verifier requires |
| `settlement.asset_address` | `USDC_ADDRESSES[network]` | USDC token contract (EIP-712 `verifyingContract`) |
| `settlement.eip712_domain` `{name, version, chain_id, verifying_contract}` | `USDC_EIP712_DOMAINS[network]` + `USDC_ADDRESSES[network]` | the complete EIP-712 domain the payer signs under |

Plus `instructions` reworded to name the exact amount + payee + token + network, and to drop the misleading "at least" (EIP-3009 transfers the *exact* signed value).

### Architecture — advertised == verified BY CONSTRUCTION
- The core generator (`packages/mcp/src/adapters/circle-nano.ts`) stays **crypto-constant-free** — it renders whatever discovery fields it's handed. Duplicating the USDC address/domain into packages/mcp would reintroduce exactly the drift class that shipped the A2 Base-Sepolia domain bug.
- The **app wrapper** (`apps/web/src/lib/circle-nano-proxy.ts`) is the canonical injector: it reads the SAME pinned constants the verifier binds to (`USDC_ADDRESSES`, `USDC_EIP712_DOMAINS`) plus `getCircleNanoRecipient()`, all keyed off one `CIRCLE_NANO_402_NETWORK` constant (`eip155:8453`). So the advertised payee/token/domain match what the verifier enforces by construction.
- **All-or-nothing**: discovery fields are emitted only when the recipient is a valid address (`isAddress(strict:false)`, matching the verifier's own guard) AND the network's asset+domain resolve — otherwise omitted (never advertise a payee/contract the rail can't honor). When `SETTLEGRID_USDC_RECIPIENT` is unset the rail is dark and the fields are absent.

### Scope decision — the FULL payer-discovery path was traced
The only **live** circle-nano 402 emitter is the production proxy route (`apps/web/src/app/api/proxy/[slug]/route.ts:~1989`, via the wrapper) — now fixed. The kernel **multi-protocol manifest** (`buildMultiProtocol402`) advertises circle-nano as a capability *teaser* with no recipient, but it is wired ONLY into the demo/sandbox route (`api/demo/kernel`, `DEMO_TOOL_SLUG='demo-sandbox-tool'`, "NO REAL MONEY") and is a two-step-discovery teaser that points payers to the single-protocol 402. Other surfaces (`.well-known/mpp.json`, `openapi.json`, learn pages) list circle-nano as a capability/enum, not a payable challenge. **No live surface was missed** (independently re-verified by the hostile reviewer's full enumeration).

## DEBT / deferred follow-ups (non-blocking)
1. **Enable-gate split (pre-existing):** the proxy routes circle-nano on `isCircleNanoEnabled()` (`CIRCLE_NANO_API_KEY`) while discovery + the verifier gate on `SETTLEGRID_USDC_RECIPIENT`. In a deploy with the API key set but the recipient unset, a circle-nano request gets a dark (discovery-less) 402. Prod has both set, so it doesn't bite. Future: align the proxy detection to `isCircleNanoKernelEnabled()`.
2. **Demo manifest enrichment (consistency):** the kernel multi-protocol 402 manifest (`buildMultiProtocol402`/`buildChallenge`) advertises circle-nano without a recipient. Demo/sandbox-only today. If the kernel dispatch is ever wired to production for circle-nano, it MUST inject discovery the way the wrapper does (see the contract note on `CircleNanoAdapter.build402Response`).
3. Carried A2 items (unchanged): move `SETTLEGRID_USDC_RECIPIENT` off the hot gas wallet to a dedicated revenue wallet (founder config); `takeBps:0`; fire-and-forget ledger writes.
