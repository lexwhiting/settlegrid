## 1. Intent — why this chunk exists

**Goal (one sentence):** stop two consumer-side endpoints from minting **real spendable money** to unauthenticated or racing callers — the **$500 academic credit** (`consumer/academic`, granted with no proof of mailbox control) and the **$25×N referral double-credit** (`consumer/referral/apply`, a check-then-act TOCTOU with no atomic guard).

**Why now / who consumes it.** These are **G3-1 + G3-2** — launch-gate MONEY/ABUSE blockers. `consumers.globalBalanceCents` is real spendable balance: the proxy **debits** it to pay for tool invocations (`proxy/[slug]/route.ts:694`, `:934`, `:2699` — `globalBalanceCents - costCents`), so every falsely-granted cent is a real platform loss at launch when consumers arrive. Both holes are trivially exploitable today:
- **G3-1:** `consumer/academic/route.ts` POST is **unauthenticated** — anyone posts `{email, institutionName}` where `email` merely *string-matches* an academic suffix (no proof they control it) and a **new consumer is created with `globalBalanceCents = 50_000` ($500)**. Plus a substring bypass: `.uni-`/`.univ-` are matched via `domain.includes('uni-')` (route.ts:61), so `x@myuni-hack.com` qualifies. Cap is only 3/day/IP (IP-rotatable) over a near-unlimited attacker-chosen email space.
- **G3-2:** `consumer/referral/apply/route.ts` IS authed, but the "already referred?" check (line 68, a SELECT) is separated from the crediting UPDATE (line 95) with **no `WHERE referred_by IS NULL` guard, no transaction, no unique constraint** → concurrent POSTs by one referee all pass the read then all run the UPDATE → **+$25×N to both referee and referrer**.

**What the output enables.** Two consumer money-grant paths that grant **exactly once, only to a party that proved control of an eligible mailbox / is entitled**, each with a **pinned regression test** so the fix stays closed under the live `web-ci` gate.

## 5. The load-bearing decisions most likely to be SILENTLY WRONG (audit concentrates here)

### LBD-1 (G3-1) — "email-verified academic session": the suffix-match MUST run on the VERIFIED SESSION email, and "verified" must actually prove mailbox control
The honest-minimum fix is *authed + email-verified + suffix-match*. The silent-wrong version passes every test yet leaves the hole open: **add `requireConsumer` but still read the academic email from the request BODY.** Then an authed consumer with any mailbox posts `body.email = victim@harvard.edu` and gets $500 — auth added, **mailbox-control proof still absent.**

**RESOLUTION (fold):** eligibility is keyed on the **authenticated + confirmed session email**, never a body field.
1. Gate the route on `requireConsumer` (401 if unauthenticated).
2. Require **email-verified**: check the Supabase user's `email_confirmed_at != null`. Since `requireConsumer` does not expose it (F5), the builder picks the minimal mechanism — either extend `requireConsumer` with an opt-in (`{ requireEmailVerified: true }`) that also returns the confirmed email, OR inline a `supabase.auth.getUser()` + `email_confirmed_at` check in the academic route (lower blast radius — only this route needs it). **Do NOT weaken `requireConsumer`'s existing callers.**
3. Run `isAcademicEmail()` on the **verified session email**, not `body.email`. Treat `body.email` as ignored-for-eligibility (keep `institutionName`/`useCase` as metadata only).
4. **SEAM / §P dependency:** email-confirmation proves mailbox control ONLY if the project's Supabase is configured to REQUIRE email confirmation at signup. If confirmation is disabled (auto-confirm), `email_confirmed_at` is always set and the check is toothless. The build cannot change a Supabase project setting → this is a **§P operator-confirm item** ("Supabase email-confirmation is ENABLED for the consumer project"). The build's job is the code gate; the operator confirms the setting.
5. Fix the **substring bypass** (F3): replace `domain.includes('uni-')`/`includes('univ-')` with a real domain-label match (a domain label that STARTS WITH `uni-`/`univ-`, e.g. split on `.` and test the label, or a bounded regex) so an arbitrary `…uni-…` substring no longer qualifies. Builder picks the exact predicate; the REQUIREMENT is *no arbitrary-substring bypass*.
**Failure mode if mis-decided:** the $500 hole stays open (body-email trust), or the verify check is toothless (Supabase auto-confirm) with no §P flag, or the substring bypass survives.

### LBD-2 (BOTH) — grant idempotency + atomicity via a conditional `UPDATE … WHERE <null-marker> … RETURNING id`, rowCount-gated, in one transaction
This is the shared seam. The silent-wrong versions: (a) crediting the **referrer OUTSIDE** the referee's rowCount gate (referrer double-credited even when the referee update no-oped); (b) **not wrapping in a txn** (a mid-failure leaves referee credited-but-unmarked, or referrer credited without referee); (c) for G3-1, **omitting the idempotency marker** entirely so an authed academic consumer re-invokes for repeated $500; (d) reading drizzle's affected-rows wrong (F7 — use `.returning({ id })` + `.length`, not an assumed `rowCount`).

**RESOLUTION (fold):**
- **G3-1 grant** — add a nullable marker `academicGrantedAt timestamp with time zone` to `consumers` (`schema.ts` + `drizzle-kit generate` → `0017_*.sql`). Grant via one atomic statement on the AUTHENTICATED consumer (no orphan `insert`):
  `UPDATE consumers SET global_balance_cents = global_balance_cents + 50000, academic_granted_at = now() WHERE id = :authId AND academic_granted_at IS NULL RETURNING id` → grant succeeded iff `.returning({id})` length === 1; length 0 ⇒ already granted ⇒ return idempotent success (no second credit). (Wrap in a txn if any additional write is added; a single conditional UPDATE is itself atomic per F10.)
- **G3-2 apply** — wrap both updates in `db.transaction`. Referee update gets the null-gate:
  `UPDATE consumers SET referred_by_consumer_id = :refId, global_balance_cents = global_balance_cents + 2500 WHERE id = :authId AND referred_by_consumer_id IS NULL RETURNING id` → if length !== 1, a concurrent apply already won ⇒ **abort the txn, credit NO ONE, return already-referred**. Credit the referrer (`+2500`) **only after** confirming the referee update hit exactly one row, **inside the same txn**. Keep the self-referral / invalid-code / already-referred fast-path checks (cheap pre-filters; the null-gate is the real guard). Per F10 the null-gate serializes concurrent applies correctly under PG default isolation — no `SELECT FOR UPDATE` needed.
**Failure mode if mis-decided:** double-credit survives (referrer outside the gate, or no null-gate), partial credit on failure (no txn), or repeated $500 (no G3-1 marker).
