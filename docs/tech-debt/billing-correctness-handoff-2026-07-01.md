## 1. Intent — why this chunk exists

**Goal (one sentence):** stop a Stripe consumer-credit webhook from **permanently skipping a paid credit** — when the credit write fails, DELETE the idempotency marker so Stripe's automatic retry re-runs and actually credits the consumer.

**Why now / who consumes it.** This is **G3-5** — a launch-gate MONEY/BILLING blocker. The Stripe webhook `billing/webhook/route.ts` records a global idempotency marker (`processedWebhookEvents`, PK `eventId`) **before** the `switch` runs (`:114-118`). If a handler's credit write then throws, the outer catch returns **500 → Stripe retries**, but the marker is already committed → the retry hits the dedup gate (`:120-125`) → returns `200 duplicate` → **the credit is skipped forever: the consumer paid but their balance was never incremented.** The `transfer.*` payout handlers already solve this (delete the marker on failure, `:675-688`/`:768-769`); `checkout.session.completed` does **not**. **Brand-asymmetry (same as G3-3):** a consumer paying and getting nothing is trust-fatal; a rare double-credit is a revenue leak. But here the dangerous direction is DOUBLE-CREDIT (see LBD-1) — the fix must close the skip WITHOUT opening a double-credit.

**Opportunistic fold — G3-4 (DEMOTED, non-gating, quality/UX):** `validateToolForActivation` (`lib/quality-gates.ts`) omits a non-null `proxy_endpoint` check → a tool can flip `active` with a null/empty endpoint → it lists and 404s on every call. The queue directs folding this here (`launch-gate-queue.md:24`). Reversible, no money.

**What the output enables.** A Stripe consumer-credit webhook that is **retry-safe** (a transient DB failure during the credit no longer permanently drops a paid credit) with a **pinned regression test**, plus a quality gate that won't activate an endpoint-less tool.

## 5. The load-bearing decisions most likely to be SILENTLY WRONG (audit concentrates here)

### LBD-1 (AUTHORITATIVE — the crux, DC-06) — delete the marker ONLY when NO credit committed
The naive reading of "delete the dedup marker on failure" is `try { …credit writes… } catch { delete marker; throw }`. That is safe for `transfer.*` **only because** its work is a single `db.transaction` (atomic — a throw commits nothing). For `checkout.session.completed` the writes are NON-transactional, so the naive wrap is safe **only if** the money write is the LAST write that can throw (the F5 invariant, which HOLDS for all three checkout paths — F4). **If a throw can occur AFTER the credit commits, delete-marker → Stripe retry → DOUBLE-CREDIT** (the exact DC-06 recurrence proxy ③ F2 just closed). **RESOLUTION (recommended):** mirror `transfer.*` EXACTLY — wrap the `checkout.session.completed` credit writes in a `db.transaction`, then `try/catch/delete-marker/re-throw` around it, so delete-on-failure is unconditionally atomic-safe and does not rest on the fragile F5 invariant. (Acceptable minimal alternative: keep the non-transactional writes but wrap in `try/catch/delete/re-throw` AND add a regression test asserting a post-credit throw does NOT delete the marker — pinning F5 against future edits. The transaction is strictly safer and is the recommendation.) **Failure mode if mis-decided:** a delete-after-committed-credit path → double-credit on retry (worse than the bug being fixed).

### LBD-2 (AUTHORITATIVE — scope) — fix `checkout.session.completed` ONLY; do NOT naively touch `payment_intent.succeeded`
`payment_intent.succeeded` (auto_refill, F6) has the same permanent-skip class but credits BEFORE a later `purchases` update — its credit is NOT the last write, so a naive delete-marker there DOUBLE-CREDITS. **RESOLUTION:** the fix covers **all three `checkout.session.completed` write paths** (subscription + credit-pack + credit-purchase — the roadmap cites the credit-pack line `:221` but all three share the hazard and F5-safety, so protect the whole case body once) and STOPS there. **Do NOT fold `payment_intent.succeeded`** — FLAG it as a separate same-class finding for a new roadmap G-row (its correct fix is a reorder-then-transaction, out of scope here). **Failure mode if mis-decided:** (a) "helpfully" extending the naive fix to `payment_intent.succeeded` → double-credit; or (b) scoping so narrowly you protect only the roadmap-cited credit-pack line and leave the credit-purchase path (`:289`) in the SAME handler exposed.

### LBD-3 (G3-4) — the non-null `proxy_endpoint` check
`validateToolForActivation` must (1) add `proxyEndpoint: tools.proxyEndpoint` to the SELECT (`:41-45`, currently absent) and (2) push a failure when `proxyEndpoint` is null OR empty/whitespace (`!tool.proxyEndpoint || tool.proxyEndpoint.trim() === ''`), mirroring the existing check style (`failures.push('A proxy endpoint (upstream URL) must be set …')`). **Failure mode if mis-decided:** (a) forgetting the SELECT addition → `tool.proxyEndpoint` is `undefined` → the check is vacuous/false-green; (b) null-only check → an all-whitespace endpoint activates and still 404s; (c) wrong column name.
