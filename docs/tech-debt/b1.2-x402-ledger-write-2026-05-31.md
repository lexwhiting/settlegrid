## KEY DESIGN DECISION — status `'pending'`, not `'settled'` (founder-greenlit)
The handoff specified `'settled'` (mirroring ap2). The independent reviewer flagged that as a **HIGH** funds-accounting bug, and verifying the actual x402 flow confirmed it:
- The x402 **proxy path** only yields an on-chain `txHash` in **facilitator mode** (`X402_FACILITATOR_URL` set). In **local mode** (current prod — gas wallet only) `validateX402Payment` does **structural acceptance** and returns **no txHash** → `buildX402SettlementRow` returns null (nothing moved on-chain to record — correct).
- Even in facilitator mode the txHash is returned on **mempool broadcast** (`settleExactPayment` does not `waitForTransactionReceipt`), so it is NOT a confirmed settlement. Recording `'settled'` would violate the money-rail invariant A2 set for circle-nano ("broadcast is NOT settlement") and could leave a permanent, uncorrectable phantom `'settled'` row (writer is FIRST-WRITE-WINS via ON CONFLICT DO NOTHING).

**Resolution:** record `'pending'` (no `settledAt`) with the broadcast `txHash` in `externalRef`; the **B1.4 reconciler** confirms the receipt on-chain and flips to `settled`/`failed` via an explicit UPDATE on `operation_id`+`rail` — exactly the circle-nano A2 flow. This makes x402 as honest as circle-nano.
